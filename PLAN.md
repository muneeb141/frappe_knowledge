# Frappe Knowledge implementation plan

This is the active plan for the local Bench. The starter's `docs/ROADMAP.md` records the earlier research milestones; this plan follows the supplied local implementation prompt and the clarified [knowledge-kit product direction](docs/PRODUCT_DIRECTION.md). Scope is Frappe, ERPNext and HRMS v16 first. `/knowledge` is the planned React dashboard route. No model provider is selected.

## Phase 2 — profile and storage contracts: first vertical slice complete

- Done: centralized source-app and compatibility-profile registry with only `frappe-v16` active. Runtime Frappe version remains separate from each indexed app's own version. New schema-3 snapshots include a profile ID and source-authored descriptions; projects and snapshots store the same profile identity, and import/retrieval reject mismatches. Schema-1/2 snapshots remain readable. The content hash is an integrity check, not a cryptographic signature of provenance.
- Done: `FK Knowledge Row` stores files, nodes/evidence, edges/evidence and lexical terms in 500-row batches with scoped indexes. New imports omit the full graph field. The existing sample was copied to indexed rows, reconstructed to its original hash and left with its JSON rollback copy. Indexed retrieval matches the original sample's ordered payroll nodes and edges.
- Measured on the three-file site sample: 30 warm reads, median 18.56 ms, p95 26.29 ms, with a 20-node context. Current limits: 20 MB HTTP import, 500 ranked title candidates, 10,000 adjacent edges per query step, 50 nodes, 3 hops and 64,000 characters. Concurrent full-corpus reads and p95 remain unmeasured; the direct full import and three query observations are recorded below.
- An offline scan of the three clean, pinned local v16 checkouts indexed 6,314 eligible files into 40,570 nodes and 38,633 edges in 16.9 seconds, with about 600 MB peak process memory. Canonical JSON was 75,040,602 bytes, beyond the HTTP import limit. It recorded 124 dynamic links requiring runtime resolution; this is still partial semantic coverage. One in-memory `Payroll Entry` context took 1.04 seconds and returned 9 nodes/1 edge under the 16,000-character budget.
- Done: an admin-only local indexing request queues a long job against clean installed apps from the profile registry; it accepts no repository paths or remote URLs and never pulls/app-upgrades. The full three-app graph was stored on `ai.localhost` as 281,306 rows in 183 seconds. A subsequent Desk-button request ran through the long worker and completed successfully in 18.61 seconds against the existing snapshot. Exact title rows and term-overlap ranking replaced the previous arbitrary hash-order candidate limit. A source-backed controller-module edge and relevance-first traversal now surface Journal Entry from Payroll Entry in the default 16,000-character context.
- Measured full-site reads on that snapshot: Payroll Entry 1.23 s (8 nodes, 6 edges), Journal Entry 1.23 s (6 nodes, 5 edges), and `get_advance_deductions` 2.32 s (exact symbol first). These are single local observations, not p95 or a held-out relevance evaluation.
- Done in the next retrieval slice: a separate `FK Source Chunk` projection stores 27,077 bounded, hash-checked Python/DocType JSON excerpts for the same installed snapshot. An InnoDB FULLTEXT index over code-normalized text returns cited source matches within the context budget. Its local footprint was about 139 MB data plus 20 MB indexes. Exact symbol evidence can pull its matching chunk. A fixed independent five-question file-retrieval check found 4/5 expected files in the first five excerpts, including 2/5 first; workflow transition validation was missed. See [retrieval evaluation](docs/RETRIEVAL_EVALUATION.md).
- Done in the following ranking slice: the workflow miss came from an absolute DocType-path preference after FULLTEXT retrieval, not missing source text. A bounded module-diversity slot for location questions brought both the original workflow query and a new wording into the returned excerpts. The earlier five-question set improved from 4/5 to 5/5 files within five excerpts; a new six-question set improved from 5/6 to 6/6 without regression on the five-question development set. These sets were inspected during tuning, so they are regression checks rather than untouched quality estimates. Two workflow citations were checked against the pinned local source lines.
- Done in the first effective-site slice: immutable, project/snapshot/site-bound `FK Site Overlay` records capture permission-visible Custom Fields and field-level Property Setters as effective field metadata. The payload stores field types, Link/Table targets, visibility/required/read-only flags, permission level and customization record references; it excludes defaults, scripts and record values. Admin-only capture/read APIs and an optional, bounded `get_context` overlay are available. On `ai.localhost`, one capture recorded 212 effective fields from 77 Custom Fields and 179 field-level Property Setters, with 8 unresolved field references and 8 other Property Setters excluded. Its `source_identity` is explicitly unverified by the overlay. This is a partial site overlay, not a complete configuration or permission model.
- Remaining before calling storage ready for broad use: evaluate a larger untouched set of natural-language questions and citation relevance, measure cold/warm p95 and concurrent reads, and add durable job state and active-snapshot publication. A large worker import checks row count and in-memory snapshot integrity; it does not yet reconstruct the entire stored graph for hash verification.
- Research decision: retain versioned JSON for exchange/integrity and indexed Frappe/MariaDB records as source of truth. Compare the present exact-title/graph/FULLTEXT pipeline with code-aware postings/BM25 before considering semantic search. FULLTEXT token rules and the 500-candidate title cap remain retrieval risks. See [storage and indexing research](docs/STORAGE_AND_INDEXING.md).
- Clarity slice: schema-3 snapshots now record bounded source-authored DocType/function descriptions with evidence locations; context JSON includes a deterministic glossary of relation codes. The new partial sample was imported on `ai.localhost` without changing the older immutable snapshot. These descriptions are source claims, not verified business behavior.

## Phase 3 — React vertical slice

Build React + TypeScript + Vite in this app at `/knowledge`, same-origin with Frappe sessions and CSRF. Ship real project/profile selection, source state, context query and evidence display for the read-only developer/support kit. Add explicit project membership and knowledge roles before support-team access. Verify production build, nested refresh, guest/session-expired and denied states. Keep unavailable model answers disabled.

## Phase 4 — corpus and payroll depth

The complete eligible local v16 source inventory has been scanned and its Python/DocType JSON text chunked, with 124 dynamic links unresolved. Improve code-aware search where evaluation shows misses, then add hooks, permissions, workflow rules, Doctype-level customizations and a reviewed HRMS payroll to ERPNext accounting workflow. The initial field-level site overlay is available, but does not yet cover those behaviors. Do not equate file inventory with semantic coverage.

## Phase 5 — one model and configuration

Ask for local-vs-cloud provider and credential choice when model work becomes the next dependency. Add a provider-neutral adapter, grounded answers, usage and budgets. A no-web-search cloud model still sends selected context to its provider; a strictly offline deployment needs a local model. No live AI claim until actual calls and failures are tested.

## Phase 6 — refresh, lessons and pilot

Extend the initial queued local reindex with durable status, idempotent refresh identity, atomic active-snapshot publication, rollback, candidate/validated/retired lessons, permission and cache isolation, then run the held-out evaluation before pilot claims. A separate reviewed-source import may later fetch upstream data; the local reindex does not.
