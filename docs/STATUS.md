# Current implementation status

Updated 19 October 2026. First release scope is a v16 host with the `frappe-v16` knowledge profile. A v15 profile and v15 runtime support are not available.

## Verified capabilities

- The app is migrated on disposable `ai.localhost` with `FK Project`, immutable `FK Snapshot`, `FK Knowledge Row`, an admin-only import/context API and a Desk JSON viewer. The viewer has an **Index installed sources** button that queues a read-only scan of clean, registered app checkouts. It reports the job ID, without durable progress tracking yet.
- The offline static indexer records source commit and file hashes, bounded source-authored descriptions, line-linked evidence, typed relationships, unresolved dynamic links and coverage limits. Context JSON explains its relation codes. It does not execute indexed source.
- A schema-3 snapshot of the installed Frappe, ERPNext and HRMS v16 checkouts was stored on the site. The scan covered 6,314 eligible files, 40,570 nodes and 39,623 edges, including a controller-module relationship; 124 dynamic links remain unresolved. The 75,040,602-byte pre-relationship scan took 16.9 seconds and about 600 MB peak process memory. The latest graph took 183 seconds to store as 281,306 rows, including exact-title lookup rows. These are local observations, not production benchmarks.
- The next slice stored 27,077 hash-checked source-text chunks in a separate, rebuildable `FK Source Chunk` table. MariaDB FULLTEXT searches normalized code words; exact graph titles still resolve symbols. Context results now include bounded excerpts with app, file, commit, hash and line citations. The table occupied about 139 MB of data plus 20 MB of indexes in this local observation.
- A fixed five-question independent source-file check found the expected implementation file within the first five excerpts for 4/5 questions (first for 2/5). It missed Frappe workflow-transition validation. See [retrieval evaluation](RETRIEVAL_EVALUATION.md). This measures file retrieval, not answer correctness.
- The workflow miss was traced to DocType-first reranking of otherwise available FULLTEXT matches. A location-question module slot now returns the cited `frappe/model/workflow.py` excerpt. On the same snapshot, the earlier five-question set improved from 4/5 to 5/5 files within five excerpts; a new six-question set improved from 5/6 to 6/6. The development set stayed at 5/5. Two workflow excerpt line ranges matched the pinned local source. These are inspected regression sets, not an untouched relevance or answer-quality estimate.
- Full-snapshot context retrieval on `ai.localhost` returned Payroll Entry in 1.23 seconds with 8 nodes/6 edges, including cited links to ERPNext Journal Entry; Journal Entry in 1.23 seconds with 6 nodes/5 edges; and `get_advance_deductions` in 2.32 seconds with the exact function ranked first. Those are single reads, not cold/warm p95 or held-out recall measurements.
- The earlier three-file sample remains available and its indexed-row reconstruction preserves the original hash. Existing schema-1/2 snapshots remain readable. A schema-3 example is at [payroll-context-explained.json](../examples/payroll-context-explained.json).
- Prior HTTP and browser checks showed unauthenticated context denied, CSRF enforcement on import, an authenticated Desk/context response, and safe literal rendering of an HTML-like query string. A live Desk check displayed **Index installed sources**, required a project, and queued the real long worker for `v16-research`. The worker log recorded success in 18.61 seconds on the already-stored snapshot, and Frappe reported the job as `finished`.
- Current verification: 27 offline tests and 8 site integration tests passed; Python compilation, migration, asset build and `git diff --check` passed. The new table and both search indexes migrated successfully; the full chunk backfill and live context queries worked. Site tests cover import/retrieval scope, exact-title ordering, cross-app context, local worker import on a small fixture, queue authorization, chunk budget/access checks, duplicate/malformed inputs, site-overlay scope and immutability, and Guest denial.
- Phase 1 clean-install gate is now verified on an isolated MariaDB 10.11 server: a second fresh Frappe site installed `frappe_knowledge`, created all three source-chunk indexes during install, migrated, and passed all 7 integration tests. The first temporary site was uninstalled and reinstalled successfully. Its initial test run exposed that fresh installs skipped the index-creating migration patches; an `after_install` hook fixes this. The 27 offline tests and asset build also passed after the fix. Both temporary sites used Frappe plus this app; ERPNext/HRMS were indexed as source, not installed on those sites. The temporary sites and database were removed after verification; `ai.localhost` was untouched.
- After the ranking change, all 27 offline and 7 `ai.localhost` integration tests passed; Python syntax compilation and `git diff --check` passed. No assets changed in this slice.
- A first effective-site metadata overlay is now stored separately from source snapshots in immutable `FK Site Overlay` records. Admin-only capture/read APIs authorize the project and source snapshot before reading permission-visible Custom Fields and Property Setters. An optional context argument adds matching effective fields within the context character budget. The live `ai.localhost` capture `f5a0ba1187069402b7efa5ac140d1db2c7f2a41119e5389a7731c05ead0e0dd0` contains 212 effective fields, from 77 Custom Fields and 179 field-level Property Setters. Eight field references did not resolve in effective metadata; eight other Property Setters are excluded. A Sales Invoice query with this overlay stayed within 4,000, 6,000 and 16,000-character budgets; the 16,000-character response included 12 site fields and two source excerpts. The overlay does not verify that the attached source snapshot matches this site's deployed code.

## Work remaining

- The eligible Python/DocType JSON inventory now has text chunks, and a separate field-level site overlay captures Custom Fields and effective field Property Setters. JavaScript, documentation, Doctype-level Property Setters, workflows, custom permissions, field defaults/conditional scripts and verified end-to-end behavior explanations are not captured. Natural-language recall and citation correctness need a larger evaluation; source text and field metadata alone do not establish running-site behavior.
- Large-worker storage validates the in-memory snapshot and row count, but does not reconstruct all 281,306 stored rows for a second hash check. Database footprint, concurrency and cold/warm p95 remain unmeasured.
- The Redis worker path has now been exercised once through the Desk button against an existing snapshot. Durable refresh status, atomic active-snapshot publication, rollback and a new-revision worker run still need end-to-end verification. The full new-snapshot store was previously invoked directly in the Bench console.
- The React `/knowledge` dashboard, support roles/membership, Q&A model, local-model offline deployment, developer tool/MCP adapter and incremental sync are future phases. No live model calls, provider credentials, Flow/FAC adapter or full support-team browser journey were tested.
